# Curo v1.0.0: synthetic HTTP and gRPC evaluation

This is a local functional resilience evaluation, not a production capacity
benchmark. All users, traffic, faults, and dependencies are synthetic.
The test harness and API implementations are private; readers cannot fully
independently reproduce this run from this report alone.

## Workloads

User identities are round-robin synthetic cohorts, not closed-loop virtual
users with sessions or think time. Users share one client per application
replica; replicas have independent, memory-only Curo state.

| Scenario | Identity cohort | Replicas | Baseline/fault requests per second | Writes | Warmup/fault/recovery seconds | Fault model |
| --- | --- | --- | --- | --- | --- | --- |
| burst | 1000 | 1 | 10 / 50 | 0% | 40 / 90 / 80 | A fivefold traffic burst accompanies an error outage. |
| healthy | 100 | 1 | 10 / 10 | 0% | 40 / 40 / 40 | Healthy steady traffic control. |
| mixed | 100 | 1 | 10 / 10 | 30% | 40 / 90 / 80 | 30% writes share an error outage with reads. |
| outage | 100 | 1 | 10 / 10 | 0% | 40 / 90 / 80 | All dependency attempts return server errors during the fault. |
| rate-limit | 100 | 1 | 10 / 10 | 0% | 40 / 90 / 30 | 30% of calls are rate limited, not server failures. |
| replicas | 400 | 4 | 20 / 20 | 0% | 40 / 90 / 80 | Four independent application replicas learn separately. |
| slow | 100 | 1 | 5 / 5 | 0% | 40 / 90 / 30 | Reads take three seconds during the fault; default timeout bounds apply. |
| sparse | 80 | 8 | 1 / 1 | 0% | 40 / 90 / 80 | One request per second is spread across eight independent replicas. |
| transient | 100 | 1 | 10 / 10 | 0% | 40 / 90 / 30 | 5% of logical calls fail on their first attempt. |

All cases use the default Curo timeout bounds (2 to 30 seconds), a 4-second
caller deadline, and a 64-call in-flight cap. HTTP uses GET and POST.
Unary gRPC uses protobuf Empty messages, an explicitly read-only Read
method, and a Write method classified as mutating; no real business data
is changed. Configured grpc-go retries are disabled.
Curo never retries gRPC calls.

A precomputed open-loop request schedule is identical across modes and
protocols. Fixed trial seeds select transient/rate-limit populations.
Faults follow each request's scheduled phase, including its retries; this
is deliberately scripted service behavior, not a stopped server or actual
network outage. Error outages return HTTP 503 or gRPC Internal.
The transient scenario fails the first server attempt for a deterministic
5% population; another attempt succeeds by construction. This favors
one-shot retries and must not be generalized to arbitrary failures.
The 5% and 30% figures are hash-selection thresholds; realized finite-run
rates can differ, as the measured success counts show.

Warmup lasts 40 seconds. Protection uses the actual library evidence
windows; no clocks, internal thresholds, or readiness rules are bypassed.
Sparse replicas can remain cold. A slot over 100 ms late or a saturated
in-flight cap invalidates a suite rather than silently changing the load.

## Interpretation and limits

Breakers protect a dependency by rejecting calls; they cannot make an
unavailable service answer successfully. Recovery is driven by application
requests carrying probes, so healthy calls can be rejected after restoration.
Read and write classes, and independent application replicas, can recover
at different times. No service restart, code repair, or failover occurs.

Transient HTTP retries can recover the injected one-shot failures, subject
to readiness and budgets. The same improvement is not expected for gRPC,
where Curo deliberately does not retry. No write should reach the dependency
twice; the runner checks this explicitly.

Rate limits are not fixed by adding retries or opening breakers. Sparse
traffic and fresh instances may not collect enough evidence to act.
Adaptive timeouts learn from retained slow samples: an initial cut does
not mean every later 3-second response will be cut. Caller deadlines remain
authoritative. Ending a slow call is a failure, not a recovered success.

This run does not cover DNS/TLS misconfiguration, stopped servers, HTTP/2
through the HTTP transport, streaming, cross-machine networking, meaningful
payload processing, service resource contention, or long-lived user sessions.
Co-located concurrent cases introduce shared-host noise. Two seeds are
functional repetitions, not a confidence interval or proof of production
reliability.

The appropriate claim is automatic client-side protection and observed
recovery under the documented synthetic conditions, not upstream repair
or a demonstrated number of real API users.
